## 초기 학습

### L-001: 데이터 제공과 투자 판단을 분리한다

- 상황: 초기 아이디어에서 뉴스·수급을 이용해 자동으로 시장을 해석하려 했다.
- 문제: 사용자는 비교와 판단을 직접 하길 원했으며 자동 해석은 제품 목적을 흐렸다.
- 규칙: 명시적 요구가 생기기 전까지 서비스는 자료 수집·정리·보관만 담당한다.
- 반영: `PRD.md`, `ADR-003`

### L-002: 테마와 업종을 같은 개념으로 취급하지 않는다

- 상황: 수급을 테마별로 집계하려 했다.
- 문제: 테마는 중복·주관적이며 공급자마다 분류가 다르다.
- 규칙: 수급 집계는 공식 업종을 사용하고, 테마는 뉴스 검색 키워드로 제한한다.
- 반영: `ADR-005`

### L-003: API 필드의 의미와 단위를 먼저 확인한다

- 문제: `netslmt`는 수량/금액 요청 모드에 따라 의미가 다르고 순위 API에는 과거 날짜 지정이 없다.
- 규칙: 공식 요청 모드·단위를 고정하고 원본 값과 정규화 값을 함께 저장한다. 과거 재조회로 오인할 UI를 만들지 않는다.
- 반영: `providers/kiwoom.py`, `tests/test_market.py`, `IMPLEMENTATION_NOTES.md`

### L-004: 실시간 중복 제거는 정상 체결을 보존해야 한다

- 문제: 같은 초·가격·수량으로 여러 정상 체결이 발생할 수 있다.
- 규칙: 누적거래량을 식별에 포함하고, 중지 이벤트는 버퍼 잠금 안에서도 재확인한다.
- 반영: `services/live.py`, `tests/test_live.py`

### L-005: 화면 테스트도 저장 이후 흐름까지 실행한다

- 문제: 브리핑을 생성한 뒤에만 실행되는 알림의 비표준 아이콘이 Streamlit 오류를 일으켰다.
- 수정: 올바른 기본 알림으로 변경하고 생성→저장→기록→설정 흐름을 AppTest로 검증했다.
- 규칙: 최초 로딩만으로 완료 판정하지 않는다.
- 반영: `tests/test_app.py`

### L-006: 공급자 이름이 같아도 발급 플랫폼별 인증 계약을 확인한다

- 상황: 사용자가 NAVER API HUB 키를 넣고 네이버 뉴스 조회를 시도했다.
- 문제: 구현은 기존 NAVER Developers Center의 URL·인증 헤더를 사용해 HTTP 401이 발생했다.
- 원인: 뉴스 검색 API라는 기능명만 확인하고 실제 키 발급 플랫폼의 호출 계약을 검증하지 않았다.
- 수정: NAVER API HUB URL·헤더로 이관하고 공급자 계약 테스트와 설정 안내를 갱신했다.
- 규칙: 키 발급 위치, 엔드포인트, 인증 헤더를 한 세트로 공식 문서와 실제 호출에서 검증한다.
- 반영: `ADR-007`, `tests/test_provider_contracts.py`, `README.md`
