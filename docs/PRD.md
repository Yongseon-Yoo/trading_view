# 대시보드 PRD

> 상태: APPROVED - 2026-09-29 사용자 구현 승인
>
> 구현 중 확정한 API 제약과 경계 처리는 `IMPLEMENTATION_NOTES.md`에 기록한다.

## 1. 제품 한 줄 설명

대시보드는 국내주식 투자자가 아침에는 관심 종목·관심 테마 뉴스를, 장 종료 후에는 외국인·기관 수급과 거래 집중 종목을 한곳에서 확인하도록 돕는 개인 데일리 리포트다.

## 2. 해결할 문제

사용자는 뉴스와 수급이 국내주식 시장 참여자의 심리와 행동을 보여주는 핵심 자료라고 본다. 그러나 관련 정보가 뉴스 검색, 증권사 화면, 종목별 수급 화면 등에 흩어져 있어 매일 반복적으로 모으는 데 시간이 많이 든다.

대시보드는 판단을 대신하지 않는다. 여러 출처의 원자료를 같은 형식으로 수집·정돈·보관하여 사용자가 직접 읽고 비교하는 시간을 줄인다.

## 3. 사용자

- 국내주식에 투자하는 개인 사용자 1인
- 관심 종목과 관심 테마를 직접 관리한다.
- 아침 장 시작 전과 장 종료 후 하루 두 번 사용한다.
- 투자 판단과 날짜 간 비교는 직접 수행한다.

## 4. 핵심 원칙

```text
뉴스 = 참여자에게 전달된 정보
수급 = 참여자가 실제로 취한 행동
가격·거래량 = 행동의 시장 결과
최종 해석 = 사용자의 책임
```

시스템은 수집, 정리, 탐색 지원, 기록만 담당한다.

### PD-013: 투자자 수급 순위 기준

- 상태: 사용자 승인
- 결정일: 2026-09-29
- 외국인·기관 순매수 및 순매도 순위는 주식 수량이 아니라 순매수금액을 기준으로 산정한다.
- 서로 주가가 다른 종목 사이의 실제 자금 유입·이탈 규모를 비교하려는 목적이다.
- 저장 시에는 원 단위의 정규화된 정수값과 공급자가 반환한 원본값·원본 단위를 함께 보존한다.
- 화면에서는 기본적으로 억원 단위로 표시하되, 정확한 금액도 확인할 수 있게 한다.
- 거래대금 순위는 당일 누적 거래대금을 기준으로 한다.

### PD-014: 업종별 수급 시각화

- 상태: 사용자 승인
- 결정일: 2026-09-29
- 저녁 리포트에 `Top 10 종목 내 업종 분포` 시각화를 제공한다.
- KOSPI와 KOSDAQ을 분리하고, 각 시장 안에서 외국인과 기관을 따로 볼 수 있게 한다.
- 시각화는 업종별 순매수금액 합계를 오른쪽 양수 막대, 순매도금액 합계를 왼쪽 음수 막대로 표현하는 양방향 가로 막대그래프로 한다.
- 막대에는 금액을 표시하고 상세 정보에는 포함 종목 수와 대표 종목을 제공한다.
- 색상만으로 매수·매도를 구분하지 않고 부호, 축 방향, 텍스트를 함께 사용한다.
- 이 집계는 전체 업종 수급이 아니라 각 투자자별 순매수·순매도 Top 10에 포함된 종목만의 분포임을 차트 제목과 안내문에 명시한다.
- 차트는 순환매나 매수 기회를 판정하지 않으며 사용자가 직접 패턴을 해석한다.

### PD-015: 시간대별 뉴스 발생량 시각화

- 상태: 사용자 승인
- 결정일: 2026-09-29
- 아침 브리핑에서 관심 종목과 관심 테마별로 시간당 기사 수 막대그래프를 제공한다.
- X축은 `Asia/Seoul` 기준 시간, Y축은 동일 URL을 제거한 기사 수로 한다.
- 각 시간대의 상세 정보에 유사 제목을 묶은 이슈 수를 함께 표시한다.
- 기사가 없는 시간도 0건으로 표시하여 뉴스가 몰린 시간과 공백을 구분할 수 있게 한다.
- 최근 1시간, 최근 6시간, 직전 장 마감 이후 전체 기사 수를 요약 수치로 함께 제공한다.
- `급증`, `호재`, `악재` 등의 자동 판정은 하지 않고 사용자가 차트와 기사 목록을 직접 해석한다.

### PD-016: 아침 종목 카드의 가격 기준

- 상태: 사용자 승인
- 결정일: 2026-09-29
- 아침 브리핑 생성 시 등록 종목의 최신 가격을 키움 REST API로 한 번 조회한다.
- 종목 카드에는 현재가 또는 전일 종가, 전일 대비 가격, 등락률, 가격 기준 시각을 표시한다.
- 장 시작 전에는 최신 가격을 `전일 종가`로 명확히 표시하고 장중에는 `조회 시점 현재가`로 표시한다.
- 가격은 브리핑 생성 시점의 스냅샷이며 자동 갱신이나 실시간 스트리밍으로 오해되지 않게 안내한다.
- 가격 조회 실패가 뉴스 수집과 브리핑 저장을 중단시키지 않으며 해당 종목 카드에 실패 상태를 표시한다.

### PD-017: 장중 관심종목 WebSocket

- 상태: 사용자 승인
- 결정일: 2026-09-29
- 별도의 `장중 관심종목` 화면에서 사용자가 등록한 종목의 키움 `0B 주식체결` WebSocket을 구독한다.
- 사용자가 `실시간 시작`과 `실시간 중지`를 직접 제어한다.
- 종목별 현재가, 등락률, 체결량, 누적거래량, 마지막 체결 시각을 실시간으로 갱신한다.
- 연결 이후 최근 5분, 종목당 최대 300건의 체결가를 메모리에 유지하여 실시간 선 그래프로 표시한다.
- 실시간 체결 이벤트는 리포트나 SQLite에 저장하지 않고 연결 종료 시 폐기한다.
- API 키가 없으면 실시간 시작을 비활성화하며, 장이 닫힌 상태에서는 실제 체결 수신을 기다린다.
- 호가잔량, 주문·체결 계좌 이벤트, 자동 알림, VI 이벤트는 MVP에서 제외한다.
- 실시간 화면은 매매 신호를 만들거나 주문을 실행하지 않는다.

### PD-018: MVP 기술 구성

- 상태: 사용자 승인
- 결정일: 2026-09-29
- Python 단일 코드베이스로 구현한다.

- 관심 종목·테마와 날짜별 리포트는 로컬 SQLite 파일에 저장한다.
- 뉴스와 수급 및 실시간 가격 차트는 Plotly를 사용한다.
- 실제 로컬 DB 파일과 API 인증정보는 GitHub에 커밋하지 않는다.
- 앱 최초 실행 시 빈 DB를 자동 생성하고 관심 목록은 사용자가 직접 등록한다.

### PD-019: 리포트 열람과 내보내기 범위

- 상태: 사용자 승인

### PD-020: API 인증정보와 데이터 모드

- 상태: 사용자 승인
- 결정일: 2026-09-29
- GitHub에는 값이 비어 있는 `.env.example`만 제공한다.
- 사용자는 로컬에서 `.env`를 만들고 발급받은 키를 직접 채운다.
- 키움과 네이버 인증정보는 서로 독립적으로 확인한다.
- 한 공급자의 필수 인증정보가 모두 있으면 해당 실제 공급자를 사용하고, 비어 있으면 해당 공급자 기능을 비활성화한다.
- 일부 값만 입력된 불완전한 설정은 실제 호출을 시도하지 않고 누락된 설정을 화면에 안내한다.
- 키움은 안전을 위해 모의투자 모드를 기본값으로 하며 사용자가 명시적으로 운영 모드를 설정할 때만 운영 엔드포인트를 사용한다.
- `.env`, 토큰, 로컬 SQLite DB는 GitHub 커밋 대상에서 제외한다.
- 실제 App Key, Secret과 토큰은 UI나 SQLite에 저장하지 않고 로그에도 출력하지 않는다.

### PD-023: 샘플 모드 종료와 실제 API 전용 운영

- 상태: 사용자 승인
- 결정일: 2026-09-30
- PD-004·017·018·020·021의 샘플 공급자·가상 체결·자동 초기 데이터 관련 결정을 대체한다.
- 뉴스·시세·수급·실시간 체결은 발급된 실제 API 인증정보가 있을 때만 조회한다. 키가 없거나 일부만 있으면 가상 데이터로 대체하지 않고 설정 필요 상태를 표시한다.
- 새 로컬 DB에는 관심 종목·테마를 자동 등록하지 않는다. 기존 DB의 관심 목록과 리포트 원본은 삭제하거나 수정하지 않는다.
- 과거 샘플 리포트는 일반 화면과 기록 목록에서 숨긴다. DB 원본은 복구 가능하도록 보존한다.
- 조회 결과가 0건이거나 API 실패 시 0건·수집 실패를 그대로 표시한다.
- 종목·테마 뉴스 차트는 데이터가 동일해도 각각 고유한 화면 키를 사용한다.

### PD-024: 명칭과 화면 디자인 전환

- 상태: 사용자 승인
- 결정일: 2026-09-30
- PD-022의 명칭을 대체한다. 사용자에게 보이는 제품명은 `대시보드`로 통일하고 `YS` 로고·문구를 제거한다.
- [참고 포트폴리오](https://kmong.com/portfolio/view/12246)의 어두운 금융 화면 분위기와 정보 밀도를 참고하되, 이미지·로고·문구·화면 구성을 복제하지 않는다.
- Streamlit과 기존 API·DB 구조는 유지하고 색상·타이포그래피·간격·카드·차트·내비게이션을 일관된 디자인 시스템으로 정리한다.
- 아침 뉴스는 요약 수치와 차트를 우선 보여주고, 긴 기사 목록은 처음 일부만 펼쳐 보이되 전체 기사에 접근 가능해야 한다.
- 가격·수급·뉴스의 출처, 기준 시각, 오류 상태는 시각 변경 후에도 유지한다.
- 데스크톱과 좁은 화면에서 핵심 글자와 조작 요소가 겹치지 않아야 한다.

## 5. 핵심 사용자 여정

### 5.1 최초 설정

1. 사용자가 관심 종목을 등록한다.
2. 관심 테마와 검색 키워드를 등록한다.
3. 시장 데이터 및 네이버 API 설정 상태를 확인한다.
4. 현재 공급자별 연결 가능 여부와 누락된 설정을 확인한다.

### 5.2 아침

1. 사용자가 `아침 브리핑 생성`을 누른다.
2. 시스템이 등록 종목의 생성 시점 가격 스냅샷을 조회한다.
3. 시스템이 직전 장 마감 이후의 종목·테마 뉴스를 수집한다.
4. 중복 기사를 묶고 발행 시각순으로 정리한다.
5. 종목·테마별 시간당 기사 수 차트를 생성한다.
6. 사용자가 가격, 기사 발생 분포, 기사 제목과 원문을 확인한다.
7. 브리핑이 날짜별로 저장된다.

### 5.3 장중

1. 사용자가 `장중 관심종목` 화면에서 `실시간 시작`을 누른다.
2. 시스템이 등록 종목의 실시간 체결을 하나의 WebSocket 연결로 구독한다.
3. 종목 카드와 최근 체결가 선 그래프가 갱신된다.
4. 사용자가 `실시간 중지`를 누르거나 화면을 닫으면 연결을 종료하고 메모리 데이터를 폐기한다.

### 5.4 장 종료 후

1. 사용자가 `장 마감 리포트 생성`을 누른다.
2. 시스템이 외국인·기관 순매수·순매도 상위 자료를 수집한다.
3. 거래대금 상위 종목을 수집한다.
4. 종목을 업종별로 묶고 `Top 10 종목 내 업종 분포` 차트로 표시한다.
5. 사용자가 원자료를 살펴보고 직접 해석한다.
6. 리포트가 날짜별로 저장된다.

- 네이버 검색 API 인증정보
- 리포트 생성 요청

- 등록 종목의 장중 실시간 현재가·등락률·체결량·누적거래량·체결 시각 및 최근 체결가 차트
- 기사 수, 중복 제거 수, 발행 시각, 출처, 원문 링크

- 거래대금 상위 종목

- 데이터 출처, 조회 시각, 오류 상태

- 거래대금 상위 표

## 8. 성공 기준

### 기능

- 종목 3개와 테마 3개를 등록하고 재시작 후 다시 볼 수 있다.
- 아침 브리핑에서 직전 장 마감 이후 뉴스가 종목·테마별로 구분된다.
- 동일 링크와 유사 제목 기사가 중복 표시되지 않는다.
- 아침 브리핑에서 종목·테마별 시간당 기사 수 차트와 가격 스냅샷을 볼 수 있다.
- 장중 화면에서 키움 WebSocket 체결 스트림을 시작·중지하고 최근 가격 차트를 볼 수 있다.
- 저녁 리포트에서 외국인·기관 매수·매도 순위를 각각 볼 수 있다.
- 수급 상위 종목을 업종별로 묶은 양방향 막대그래프를 볼 수 있다.
- 생성된 리포트를 날짜와 종류로 다시 열 수 있다.

### 품질

- API 키가 저장소에 포함되지 않는다.
- 한 데이터 공급자가 실패해도 나머지 화면은 표시된다.
- 모든 외부 데이터에 조회 시각과 출처가 표시된다.
- 핵심 서비스 로직 단위 테스트가 통과한다.
- API 키가 없으면 가상 데이터 없이 설정 필요 상태를 확인할 수 있다.

## 9. 제약

- 1일 내 완성 가능한 MVP로 제한한다.
- Python과 Streamlit을 사용한다.
- SQLite 외 별도 데이터베이스를 도입하지 않는다.
- 조회 API만 사용하고 주문 API는 호출하지 않는다.
- API 공급자 응답을 도메인 모델로 변환하여 UI에서 직접 다루지 않는다.
- 뉴스 본문은 저장하지 않고 제목·출처·시각·링크 등 메타데이터만 저장한다.

## 10. 주요 엣지 케이스

- API 키가 없거나 잘못된 경우
- API 호출 제한 또는 일시 장애
- 뉴스 검색 결과가 없는 경우
- 발행 시각 형식이 잘못된 경우
- 동일 기사가 다른 URL이나 제목으로 반복되는 경우
- 장 마감 후 첫 거래일이 휴일 또는 월요일인 경우
- 수급 데이터가 잠정치이거나 일부 항목만 제공되는 경우
- 종목코드가 잘못되었거나 상장폐지된 경우
- 일부 데이터만 성공한 상태에서 리포트를 저장하는 경우
