# Architecture Decision Records

> 상태: APPROVED - 2026-09-29 사용자 구현 승인

## ADR-001: Streamlit 기반 로컬 단일 사용자 앱

- 상태: 사용자 승인
- 맥락: 1일 내 시각적 MVP와 GitHub 포트폴리오를 완성해야 한다.
- 결정: Python + Streamlit 단일 애플리케이션을 사용한다.
- 이유: 데이터 처리와 UI를 빠르게 통합할 수 있고 배포 없이 로컬 실행이 가능하다.
- 포기한 것: 복잡한 프론트엔드 상호작용, 다중 사용자, 세밀한 API 서버 경계.
- 재검토 조건: 외부 배포 또는 다중 사용자가 필요해질 때.

## ADR-002: SQLite에 원자료가 아닌 리포트 스냅샷 저장

- 상태: 사용자 승인
- 맥락: 사용자는 날짜별 리포트를 직접 열어 비교하려 한다.
- 결정: 정규화한 핵심 데이터와 생성된 리포트 JSON을 SQLite에 저장한다.
- 이유: 과거 리포트가 새 API 결과에 의해 바뀌지 않고 구현이 단순하다.
- 포기한 것: 대규모 시계열 분석과 고성능 집계.
- 재검토 조건: 장기간 전 종목 데이터를 저장하게 될 때.

## ADR-003: 판단하지 않는 Human-in-the-loop 제품

- 상태: 사용자 승인
- 맥락: 뉴스 영향, 수급 비교, 순환매 판단은 사용자 본인이 하기를 원한다.
- 결정: 시스템은 원자료를 정리하고 순위를 제공하되 호재·악재, 매수·매도, 순환매를 판정하지 않는다.
- 이유: 제품 목적과 일치하며 설명하기 어려운 자동 판단과 투자 오인을 피한다.
- 포기한 것: AI 감성 분석, 투자 신호, 자동 알림 추천.
- 재검토 조건: 사용자가 명시적인 규칙과 검증 기준을 정의할 때.

## ADR-004: Provider 인터페이스와 샘플 데이터 모드

- 상태: Provider 인터페이스는 유지, 샘플 데이터 모드는 ADR-011로 폐기
- 맥락: API 키 발급, 호출 제한, 장 운영시간 때문에 실제 데이터만 의존하면 개발과 리뷰가 불안정하다.
- 결정: NewsProvider와 MarketProvider 인터페이스를 만들고, 선정된 증권사 공급자와 SampleProvider를 함께 제공한다. 제품은 특정 증권사 API에 고정하지 않는다.
- 이유: 키가 없어도 전체 데모와 테스트가 가능하며 NH선물 API로 교체하기 쉽다.
- 포기한 것: 초기 파일 수 증가와 변환 계층 구현 비용.
- 재검토 조건: 없음. 프로젝트 확장성을 위한 핵심 결정이다.

## ADR-005: 테마 수급 대신 업종별 모아보기

- 상태: 사용자 승인
- 맥락: 테마는 중복되고 공급자별 분류가 달라 전체 시장 수급을 정확하게 계산하기 어렵다.
- 결정: 수급은 공식 업종명으로 묶고, 테마는 사용자가 등록한 뉴스 검색 키워드에만 사용한다.
- 이유: 데이터 의미를 과장하지 않고 하루 MVP에서 재현 가능한 결과를 만든다.
- 포기한 것: 자동 테마 순환매 지도.
- 재검토 조건: 검증된 테마-종목 매핑 공급자를 확보할 때.

## ADR-006: MVP 시장 데이터 공급자로 키움증권 REST API 선택

- 상태: 사용자 승인
- 맥락: 키움증권, 한국투자증권, LS증권 중 한 곳을 선택해야 하며 사용자는 세 곳 모두 신규 키 발급이 필요하다.
- 결정: MVP의 MarketProvider 구현체로 키움증권 REST API를 선택한다.
- 이유: 국내주식 시세, 거래대금 순위, 외국인·기관 수급, 종목·업종 정보를 REST API와 공식 예제로 제공한다.
- 포기한 것: 다른 증권사 API의 상품 범위와 샘플을 동시에 지원하는 것.
- 안전장치: 계좌와 키가 없어도 SampleMarketProvider로 전체 앱과 테스트가 동작해야 한다.
- 재검토 조건: 필요한 수급 데이터가 키움 API에서 제공되지 않거나 키 발급이 일정 내 불가능할 때.

## ADR-007: MVP 뉴스 공급자로 네이버 뉴스 검색 API 선택

- 상태: 사용자 승인
- 맥락: 관심 종목과 관심 테마의 장 마감 이후 기사 제목·출처·시각·링크가 필요하다.
- 결정: MVP의 NewsProvider 구현체로 NAVER API HUB 뉴스 검색 API를 선택한다. 기존 Developers Center API와 다른 호출 주소(`/search/v1/news`)와 인증 헤더(`X-NCP-APIGW-API-KEY-ID`, `X-NCP-APIGW-API-KEY`)를 사용한다.
- 이유: 공식 REST API로 필요한 뉴스 메타데이터를 제공하며 기사 본문 크롤링이 필요하지 않다.
- 포기한 것: 전체 언론시장 완전 수집, 기사 본문 분석, 복수 뉴스 공급자 교차검증.
- 제한: 결과는 네이버 뉴스 검색 범위와 정렬 정책의 영향을 받는다.
- 재검토 조건: 검색 누락이 핵심 사용자 경험을 해치거나 다른 공식 공급자가 필요할 때.
- 이관 근거: [NAVER API HUB 이관 가이드](https://guide.ncloud-docs.com/docs/apihub-migration). 두 플랫폼의 키는 서로 호환되지 않는다.

## ADR-008: 키움 WebSocket은 장중 관심종목 체결에 한정

- 상태: WebSocket 범위는 유지, SampleRealtimeProvider 결정은 ADR-011로 폐기
- 맥락: REST 기반 아침·저녁 리포트 외에 실시간 데이터 처리 역량을 포트폴리오에서 보여주고 싶다.
- 결정: 키움 `0B 주식체결` WebSocket과 SampleRealtimeProvider를 RealtimeMarketProvider 뒤에 구현하고 별도 장중 화면에서 수동으로 시작·중지한다.
- 이유: 등록 종목이라는 기존 사용자 데이터와 자연스럽게 연결되며 현재가, 등락률, 거래량을 즉시 확인할 수 있다.
- 포기한 것: 호가잔량, 계좌 주문·체결, VI 이벤트, 백그라운드 알림, 전체 체결 이력 저장.
- 안전장치: 주문 API는 구현하지 않고 이벤트는 제한된 메모리 버퍼에만 보관한다.
- 재검토 조건: 호가 기반 분석이나 실시간 규칙 알림의 검증 기준이 별도 스펙으로 정의될 때.

## ADR-009: Plotly 기반 대화형 차트

- 상태: 사용자 승인
- 맥락: 뉴스 발생량, 업종별 수급과 장중 체결가를 같은 로컬 웹 대시보드에서 시각화해야 한다.
- 결정: Streamlit 화면의 차트 라이브러리로 Plotly를 사용한다.
- 이유: Python 데이터와 직접 연결되고 툴팁, 양방향 막대, 실시간 선 그래프를 별도 프론트엔드 없이 구현할 수 있다.
- 포기한 것: 프론트엔드 전용 차트 라이브러리 수준의 세밀한 상호작용과 디자인 제어.
- 재검토 조건: React 등 별도 프론트엔드를 도입할 때.

## ADR-010: 환경변수 기반 인증과 공급자별 자동 샘플 모드

- 상태: 환경변수 인증은 유지, 자동 샘플 모드는 ADR-011로 폐기
- 맥락: 키움과 네이버 키는 이후 발급하며, 키가 없는 현재도 구현·테스트·심사 시연이 가능해야 한다.
- 결정: 빈 `.env.example`을 제공하고 실제 값은 Git에서 제외된 로컬 `.env`에서만 읽는다. 공급자별 필수 키가 완전하면 실제 모드, 모두 비어 있으면 샘플 모드로 선택한다.
- 이유: 뉴스와 시장 데이터 중 한쪽 키만 있어도 나머지 기능을 독립적으로 실행할 수 있고 비밀정보 유출을 방지한다.
- 포기한 것: UI에서 인증정보를 입력·저장하는 편의성과 중앙 비밀정보 관리.
- 안전장치: 불완전한 키 조합은 실제 호출하지 않으며, 키움 기본 환경은 모의투자로 한다.
- 재검토 조건: 외부 배포나 다중 사용자 인증이 필요해질 때.

## ADR-011: 실제 API 전용으로 전환하고 과거 가상 리포트는 비파괴적으로 숨김

- 상태: 사용자 승인
- 맥락: 네이버와 키움 인증정보가 마련되었고, 가상 데이터가 실제 조회 결과처럼 보이는 혼란이 발생했다. 동일한 0건 차트가 Streamlit 자동 ID 충돌도 일으켰다.
- 결정: ADR-004·008·010의 런타임 샘플 분기를 폐기한다. 인증정보가 없거나 실패하면 명시적 설정·오류·빈 상태를 보여준다. 차트에는 종목/테마·시장/투자자별 고유 키를 부여한다.
- 기존 데이터: 과거 샘플 스냅샷은 일반 조회에서만 제외하고 SQLite에서 삭제하지 않는다. 관심 목록은 보존한다.
- 이유: 가상 데이터와 실제 데이터를 혼동하지 않고 사용자 기록을 손실하지 않는다.
- 포기한 것: 키 없이 모든 화면을 시연하는 오프라인 데모.

## ADR-012: 독립적인 다크 금융 대시보드 디자인 시스템

- 상태: 사용자 승인
- 맥락: 기존 화면은 가격 카드와 기사 목록이 커서 핵심 지표·시간 분포를 빠르게 읽기 어렵다. 사용자는 참고 포트폴리오의 정돈된 금융 화면을 선호하지만 이름에 `YS`를 원하지 않는다.
- 결정: `docs/DESIGN_SYSTEM.md`를 단일 시각 규칙으로 두고 Streamlit 공식 테마와 앱 CSS·Plotly 스타일을 함께 적용한다. 화면 이름은 `대시보드`로 통일한다.
- 이유: Python 단일 코드베이스와 기능을 보존하면서 다섯 화면의 시각적 일관성을 높일 수 있다.
- 포기한 것: 참고 이미지의 픽셀 단위 재현 및 React 프론트엔드 재구축.
- 안전장치: 원본 이미지·로고·문구를 가져오지 않고, 투자 데이터의 출처와 상태를 숨기지 않는다.
